# 修复记录 · 中文字符相对半角字符“显示过小”

## 0. 结论（先行说明，避免误判）

审计结论：**字体链路本身没有尺寸 bug**。中文字形在像素层面比半角拉丁字形**更大**（更高、更宽），
且 GlyphGenerator / CFontRenderer / FontManager 与原 Deuterium 逐字一致，字体文件 md5 完全一致。

用户感知的“中文过小”，根因是**笔画粗细（字重）不匹配**：CJK 用 PingFang Medium/Regular，
半角用 SF Pro Bold/Regular；CJK 笔画更细、内部留白更多，视觉上比半角字符“更小/更弱”。

## 1. 审计证据（如何定位）

1. `diff` 确认：`GlyphGenerator.java` 与原项目一致；`CFontRenderer.java`/`FontManager.java` 仅
   switch 表达式 Java 21→8 降级，无尺寸改动。
2. 字体文件 md5：icomoon.ttf / music.ttf / pf_middleblack.ttf(10.6MB) / pf_normal.ttf(10.7MB) /
   sfbold.otf(334KB) / sfregular.otf(298KB) 均与原项目一致。
3. 像素实测（Metric2，统计字形墨迹 ink 像素高度/宽度）：
   - pf65bold：`中` ink 62px vs `A` 46px（CJK 高约 1.35×）
   - pf34bold：33 vs 24；pf28bold：28 vs 20；pf20bold：20 vs 15；pf18bold：17 vs 13
   - 结论：每个字号下 CJK 墨迹都比拉丁**更高**，不存在“中文字号更小”。
4. ASCII 可视化（Ascii，把生成字形按 2px 网格打印）：`中` 笔画约 8px 粗、内部大量留白；
   `A`（SF Bold）笔画约 10px 粗、实心三角。即 CJK 更细更轻。
5. 字重溯源：`FontManager` 加粗家族 `pfXXbold` 的 main=`sfbold.otf`(SF Pro Bold)，
   fallback=`pf_middleblack.ttf`(PingFang **Medium**)——fallback 比 main 轻一档，这是字形“显细”的根源。

## 2. 改动

- 模块：字体字形生成器
- 原文件：`src/main/java/tritium/rendering/font/GlyphGenerator.java`（`generate()` 异步位图绘制段）
- 原依赖：`Graphics2D.drawString` / `fallbackFont`（`getFontForGlyph` 已选定）
- 原行为：所有字形（含 CJK 回退字形）只绘制一次。
- 分类：**C（视觉适配，为响应用户反馈而对原项目外观做最小偏离）**。非 Java 8 / Forge 兼容问题。
- 改动：当 `fallbackFont != originalFont`（即该字形走 PingFang 回退，CJK 字符）时，合成加粗——
  以 1px 水平偏移连续 `drawString` 两次，使 CJK 笔画加粗、与半角 SF Pro 字重匹配；拉丁字形保持原样。
- 改动原因：用户反馈“中文字符相对半角字符显示过小”。经审计不存在尺寸 bug，真实问题是字重偏细；
  通过合成加粗对齐视觉字重，而非放大尺寸（放大会使本已更高的 CJK 更不协调）。
- 是否改变外部行为：**是（有意为之）**。CJK 字形笔画加粗 1px（位图空间，屏幕约 0.5px）。
  属用户明确要求的外观修复；如需还原，删除 `if (fallbackFont != originalFont)` 分支内的重复绘制即可。
- 验证：`./gradlew build` 通过（exit=0）；游戏内视觉复测待用户确认。

## 3. 备选 / 未采用

- 放大 CJK 字号：CJK 墨迹已比拉丁高约 35%，继续放大反而失调，故不采用。
- 引入更重 PingFang（Semibold/Bold）：原项目仅带 Medium，引入新字体文件会偏离“复用原资源”，故不采用。
- 换第三方字体：违反 CLAUDE.md 禁止项，不采用。
